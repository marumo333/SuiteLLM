# nanoquant-glm

対象は GLM-5.3-Flash（321,323,031,390 パラメータ、アクティブ 18B、45 層、ルーティングされるエキスパート 288、top-8）を、このデスクトップで推論できる格納形式にすること。手法は Samsung Research の NanoQuant（arXiv:2602.06694、2026-02）である。低ランクの二値分解で、各線形層を次の形にする。

`W ≈ s1 ⊙ (U±1 V±1^T) ⊙ s2^T`

U と V は ±1 の行列、s1 と s2 は全精度のスケールである。独立した 1bit 保存の下限（このモデルで 40,165,378,924 バイト、約 37.4 GiB）は、この分解には効かない。LittleBit（NeurIPS 2025）は同じ因子化の QAT で、公開実験は 7B〜13B 級かつ大量トークンを使う。最初の実装には入れない。

実装済みの契約は格納量である。次に測るのは 1 行列の再構成誤差である。GLM-5.3 に NanoQuant を当てた perplexity は、まだ無い。

## 構成

機械は AMD Ryzen 7 5700X、RAM 32GiB、NVIDIA GeForce RTX 4060 8GiB、ストレージ表記 932GB。

論文が圧縮を走らせた機械は H100 80GB が 1 枚で、対象は Llama / Qwen / Gemma の dense、最大 70B、校正は WikiText-2 の 128 サンプル（0.26M トークン）、Llama-2-70B で約 13 時間である。推論の実測は RTX 3050 8GB で、圧縮後の Llama-2-70B が最大 20.11 tok/s。本文のファイルサイズは 137.95 GB から 5.75 GB。要旨の別表記は 138.04 GB から 5.35 GB。ここでの比率は本文の 5.75 / 137.95 を使う。

WikiText-2 perplexity は Llama-2-70B の FP16 が 3.32、NanoQuant 0.80 bit が 7.61、0.55 bit が 9.82 である。GLM で同じ落ち方になるかは、パックしたチェックポイントができたあとの測定で決める。

親の重みは公式の FP8 リリース（約 328GB、索引の `total_size` は 328,326,771,576 バイト）を層ごとに読む。量子化は FP8、ブロックは 128×128、スケールは `weight_scale_inv` である。同じファイルに BF16 のテンソルがあるときは、その値を重みとして読む。BF16 の全量チェックポイント（約 642GB）は作業用に持たない。1 つのエキスパート行列は 4060 の 8GiB に入る。モデル全体は入らない。分解は行列ごとで、結果だけをパックしてディスクへ書く。

実行の段は次の 3 つ。

1. `features/nanoquant-glm/estimate.mjs` が、ビット幅と論文の圧縮率からバイト数を出し、32GiB の RAM（予約 4GiB）と 8GiB の VRAM に収まるかを返す。この段は実装済み。
2. FP8 から 1 行列だけを読み、ADMM で初期化し、再構成誤差を記録する。校正も、前の層の順伝播も、全層も、この段では走らせない。
3. 分解する重みを行列ごとにパックしたチェックポイントへ書く。前のブロックの量子化誤差を、次のブロックのまだ分解していない重みで吸収する手順と、校正は、まだ決めていない。推論カーネルは論文の CUDA GEMV を 4060 へ移す前に、5700X の CPU で因子の行列ベクトル積を計算して perplexity を取る。

### 分解する重み

パックに入れるテンソルは、親チェックポイントの索引で次をすべて満たすものである。

- キーが `.weight` で終わる
- 次元が 2 で、行数と列数がどちらも 32 以上
- キーが `lm_head.weight`、`model.language_model.embed_tokens.weight`、または `model.language_model.layers.N.`（N は 0 以上 44 以下）で始まる

この 3 つのキーが索引に無いときは、パックを新規作成しない。`weight_scale_inv`、1 次元の正規化とバイアス、3 次元以上の conv、層 45、`language_model` と `lm_head` の外にある画像用の塔は、分解しない。

各テンソルは、そのテンソルの重みだけから U、V、s1、s2 を作る。層をまたいで因子を共有しない。選ばれなかったエキスパートも、自分の行列として分解する。公式ファイルの中で BF16 のテンソルは、その値を重みとして読む。FP8 のテンソルは、同じ接頭辞の `weight_scale_inv` を 128×128 ブロックで掛けてから分解する。BF16 の全量チェックポイント（約 642GB）は取らない。

ルーティングされるエキスパートの線形層は 42 層 × 288 体 × 3 射影で、要素数 304,405,807,104 である。ファイル全体は 328,326,771,576 バイトなので、それ以外は 23,920,964,472 バイトである。このエキスパートだけを一様な 0.55 bit で持つと 304,405,807,104 × 550 / 8000 = 20,927,899,238.4 バイトで、残りを公式の dtype のまま足すと 44,848,863,710.4 バイト（約 41.8 GiB）になり、32GiB に入らない。321,323,031,390 パラメータ全体の 0.55 bit 見積もりは 22,090,958,409 バイトで、予約 4GiB を足しても 32GiB に収まる。画像用の塔と層 45 を外すと、この見積もりより小さい。索引で行列ごとに足した実バイトは、まだ契約にしていない。

1 行列の段は、この集合の中の 1 枚だけを測る。ゲートは行列ごとにランク、格納ビット、有限性を見る。再構成誤差の大小は合否にしない。論文の 0.55 bit の perplexity 9.82 は、前のブロックの誤差を吸収したあとの Llama-2-70B の値である。その吸収を入れない分解は、これより大きく落ちる。GLM の合格値は、この 9.82 でも、0.80 bit の 7.61 でもない。

### ビット予算

`bitsPerWeightMilli` は行列で分ける。キーに `.mlp.experts.` を含む分解する重みは 550、それ以外の分解する重みは 800 である。共有エキスパートのキーは `.mlp.shared_experts.` なので 800 である。1 行列の段の down 射影は `.mlp.experts.` に含まれるので 550 のままである。

エキスパート 304,405,807,104 要素を 800 にすると 30,440,580,711 バイトになり、32GiB から予約 4GiB を引いた 30,064,771,072 バイトを超える。550 にすると 20,927,899,239 バイトである。それ以外を最大 16,917,224,286 要素まで 800 にすると 1,691,722,429 バイトで、合計の上限は 22,619,621,668 バイトである。予約 4GiB を足しても 32GiB に収まる。画像用の塔と層 45 はこの 16,917,224,286 に含まれ、パックからは外すので、実バイトは上限より小さい。

パラメータ数でならすと、エキスパートの実効 0.52734375 bit と、それ以外の予算 0.80 bit で、平均は約 0.54 bit である。0.527 bit はエキスパート 1 枚の実効であり、モデル全体のビット数ではない。4 bit の全体は 160,661,515,695 バイトで、この RAM 常駐には入らない。使える RAM に全パラメータを置くときの平均の上限は約 0.75 bit である。

### 1 行列

測る行列は、最初の sparse 層の、ルーティングされるエキスパート 0 の down 射影である。`mlp_layer_types` の先頭 3 層は dense なので、層番号は 3（0 始まり）である。テンソル名は `model.language_model.layers.3.mlp.experts.0.down_proj.weight` と、同じ接頭辞の `weight_scale_inv` である。形は出力 4096 × 入力 2048（`hidden_size` × `moe_intermediate_size`）である。gate と up と共有エキスパートは、この 1 枚には入れない。

復元は、FP8 の値に同じ 128×128 ブロックの `weight_scale_inv` を掛けて FP32 にする。形が 4096×2048 でないとき、または復元が非有限のときは、再構成誤差を記録しない。

ランクは公開実装（SamsungLabs/NanoQuant、コミット `a9e0a430881ff80d83b622c3129e330dc33c04f5` の `calculate_ranks`）に合わせる。行数 `rows`、列数 `cols`、`bitsPerWeightMilli` に対し、

`raw = floor(rows * cols * bitsPerWeightMilli / (1000 * (rows + cols))) - 16`

とし、`raw` を 32 の倍数へ切り下げる。結果が 32 未満なら 32、`min(rows, cols)` を超えるならそこへ切る。スケールは 2 本（s1 と s2）なので、引く 16 は FP16 のスケール 1 本分である。

この行列を実効 0.55 bit（`bitsPerWeightMilli` 550）で見ると `raw` は 734、ランクは 704 である。格納ビットは `(704 + 16) * (4096 + 2048) = 4,423,680`、バイト数は 552,960 である。32 の倍数へ切ったので、この 1 枚の実効ビットは 135/256 = 0.52734375 であり、550 ミリビットの予算以下である。0.80 bit はモデル全体が予約 4GiB を足すと 32GiB に収まらないので、この 1 枚のランクには使わない。

ゲートが判定するのは、この形と 550 に対するランク 704 と、格納ビット 4,423,680 と、記録が次の形を満たすことである。親チェックポイントとパックした重みはゲートの入力にしない。再構成誤差の大小も合否にしない。記録があるとき、クラウドの親とゲートは同じ項目を読む。

ADMM の数値は同じコミットの既定に固定する。外側 400、内側 5（SVID のべき乗法）、`reg` は 0.03、ペナルティは線形でステップ `t / 400`（`t` は 0 から 399）、乱数種は 0。入力側と出力側のプレコンディショナは長さ `cols` と `rows` の 1 である。論文の Hessian 対角は校正の活性化から作る。親は約 328GB で 32GiB に載らず、1 枚の誤差を見る前に前段を走らせるとこの段の範囲を外す。校正はパックしたチェックポイントを作る段まで持たない。

ソルバ本体はこのリポジトリへコピーしない。デスクトップの測定は、固定したコミットの `factorize_admm_nanoquant` を、復元したこの 1 枚に対して呼ぶ。

再構成誤差は `‖W − Ŵ‖_F / ‖W‖_F` である。Ŵ は、均衡化のあとの因子 A（4096×704）と B（704×2048）について、符号の 0 を +1 にした U±1 と V±1、行ごとの平均絶対値 s1、列ごとの平均絶対値 s2 から `s1 ⊙ (U±1 V±1^T) ⊙ s2^T` で作る。連続因子の比は `‖W − AB‖_F / ‖W‖_F` で、同じ記録に残し、ゲートの合否には使わない。W のフロベニウスノルムが 0、または比が非有限のときは、記録を残さない。有限な比に上限は置かない。この段の誤差は、Llama-2-70B の perplexity の落ち方の代理にしない。

記録は `features/nanoquant-glm/one-matrix.json` に書き、手元の測定のあとコミットする。中身は `tensor`、`rows`、`cols`、`rank`、`bitsPerWeightMilli`、`storedBits`、`relativeError`（再構成誤差）、`continuousRelativeError`（連続因子の比）、`solverCommit`、`seed`、`device` である。ファイルが無い間は、ランクと格納ビットの契約だけをゲートが見る。ファイルがあるとき、親とゲートは次を満たすことを見る。`tensor` が層 3 エキスパート 0 の down 射影である。`rows` が 4096、`cols` が 2048、`rank` が 704、`bitsPerWeightMilli` が 550、`storedBits` が 4423680 である。`relativeError` と `continuousRelativeError` が有限である。`solverCommit` が `a9e0a430881ff80d83b622c3129e330dc33c04f5`、`seed` が 0、`device` がこの機械の GPU である。クラウドはこの JSON を再計算しない。

公式 FP8 のシャードとパックしたチェックポイントは git に入れない。`.tools/` は OPA と ripgrep の取得先で、測定の置き場にはしない。

## データの流れ

親チェックポイントはディスクに置く。932GB の表記容量に対し、FP8 の約 328GB と出力の約 30GB が入る空きが要る。空きが足りないときは、読んだシャードを分解のあと消す。1 行列の段は、そのテンソルを含むシャードだけを読み、誤差を書いたあとにシャードを消してよい。他のテンソルは展開しない。

分解する重みは、FP8 なら `weight_scale_inv` を掛け、BF16 ならその値のまま読み、連続因子とスケールを作り、±1 に量子化し、ビットパックする。校正活性化は、パックしたチェックポイントを作る段で 128 サンプル分だけを保持する。グローバルなスケール調整は、パック済みの二値を固定したまま行う。論文が 70B を 1 GPU に載せられたのは、この固定があるためである。前のブロックの誤差を次のブロックの重みで吸収する手順は、まだ決めていない。

出力チェックポイントの見込みは次のとおり。予約 4GiB は OS とランタイム用で、KV は別である。

| 見積もり | 重み | 32GiB RAM（予約 4GiB 後） | 8GiB VRAM |
| --- | ---: | --- | --- |
| 実効 0.55 bit | 22,090,958,409 バイト | 収まる | 収まらない |
| 論文比率を BF16 641.64 GB に適用 | 26,744,690,105 バイト | 収まる | 収まらない |
| 実効 0.80 bit | 32,132,303,139 バイト | 予約を足すと収まらない | 収まらない |

推論時はパックしたチェックポイントを RAM に置き、よく使う因子だけを 8GiB の VRAM に載せる。全量を VRAM に常駐させる段は、この機械には無い。

## 失敗時に残るもの

1. 提出前に基準を満たさないとき、状態は変わらない。親シャードが読めない、テンソル名が無い、形が 4096×2048 でない、復元が非有限、または 1 行列の再構成誤差が有限でないときは、誤差の記録もパックしたチェックポイントも新規作成しない。校正サンプル 128 は、パックしたチェックポイントを新規作成するときの基準である。1 行列の再構成誤差には要しない。
2. 書き戻しが失敗したとき、状態は変わらない。ADMM が非有限になった、またはパックの書き込みが途中で落ちたときは、直前の完成チェックポイントを残し、途中ファイルは捨てる。誤差の記録が途中ならそれも捨てる。
3. 状態が変わったあと、副作用だけが失敗することがある。誤差の記録が書けたあと表示が落ちても、記録は残る。チェックポイントが書けたあと perplexity の測定が落ちても、チェックポイントは残る。測定ファイルが無い状態を、品質が出たことには数えない。

`node scripts/start-feature.mjs` はこのハーネス上では機能ファイルを作らない。この設計は手で置いた。プロダクト remote で `init.mjs --product` を走らせると `docs/architecture` と cycle の蓄積が消え、ハーネスのテストが赤になる。クラウドの `install` はこの初期化のあと `git checkout -- docs cycle` で戻す。コミットした cycle は `C-0001` だけである。
