# nanoquant-glm

対象は GLM-5.3-Flash（321,323,031,390 パラメータ、アクティブ 18B、45 層、ルーティングされるエキスパート 288、top-8）を、このデスクトップで推論できる格納形式にすること。手法は Samsung Research の NanoQuant（arXiv:2602.06694、2026-02）である。低ランクの二値分解で、各線形層を次の形にする。

`W ≈ s1 ⊙ (U±1 V±1^T) ⊙ s2^T`

U と V は ±1 の行列、s1 と s2 は全精度のスケールである。独立した 1bit 保存の下限（このモデルで 40,165,378,924 バイト、約 37.4 GiB）は、この分解には効かない。LittleBit（NeurIPS 2025）は同じ因子化の QAT で、公開実験は 7B〜13B 級かつ大量トークンを使う。最初の実装には入れない。

実装済みの契約は格納量である。次に測るのは 1 行列の再構成誤差である。パックの前後で、同じ 256 トークンと同じ 3 文を親チェックポイントとパックで比べる記録は、量子化後の測定の節で固定した。数値はまだ無い。

## 構成

機械は AMD Ryzen 7 5700X、RAM 32GiB、NVIDIA GeForce RTX 4060 8GiB、ストレージ表記 932GB。

論文が圧縮を走らせた機械は H100 80GB が 1 枚で、対象は Llama / Qwen / Gemma の dense、最大 70B、校正は WikiText-2 の 128 サンプル（0.26M トークン）、Llama-2-70B で約 13 時間である。推論の実測は RTX 3050 8GB で、圧縮後の Llama-2-70B が最大 20.11 tok/s。本文のファイルサイズは 137.95 GB から 5.75 GB。要旨の別表記は 138.04 GB から 5.35 GB。ここでの比率は本文の 5.75 / 137.95 を使う。

WikiText-2 perplexity は Llama-2-70B の FP16 が 3.32、NanoQuant 0.80 bit が 7.61、0.55 bit が 9.82 である。この 3 つは GLM の合格値にしない。

親の重みは `dealignai/GLM-5.3-Flash-UNCENSORED-FP8` を層ごとに読む。元の `zai-org/GLM-5.3-Flash` は使わない。索引の `total_size` は 328,326,771,576 バイト、シャードは 62、テンソルは 76,108 で、ブロック FP8（128×128、`weight_scale_inv`）である。同じファイルに BF16 のテンソルがあるときは、その値を重みとして読む。BF16 の全量チェックポイント（約 642GB）は作業用に持たない。

この機械では親のまま推論しない。62 シャードのヘッダを足すと、ルーティングされるエキスパートの重みは 311,653,564,416 バイトである。言語モデルの常駐分（埋め込み、attention、dense 3 層、共有エキスパート、それ以外の非エキスパート）は 15,226,024,184 バイトで、8GiB の VRAM より大きい。1 トークンが触る言語層のエキスパートは 8,455,716,864 バイトで、エキスパート全体は 32GiB に入らない。公開されている起動は複数枚の H200 上の native FP8 である。量子化は、パックした重みをこの機械の RAM に置いて推論するための段である。

1 つのエキスパート行列は 4060 の 8GiB に入る。モデル全体は入らない。分解は行列ごとで、結果だけをパックしてディスクへ書く。

実行の段は次の 3 つ。

1. `features/nanoquant-glm/estimate.mjs` が、ビット幅と論文の圧縮率からバイト数を出し、32GiB の RAM（予約 4GiB）と 8GiB の VRAM に収まるかを返す。この段は実装済み。
2. FP8 から 1 行列だけを読み、ADMM で初期化し、再構成誤差を記録する。校正も、前の層の順伝播も、全層も、この段では走らせない。
3. 埋め込み、層 0 から 44、`lm_head` の順にパックする。校正、誤差の吸収、パックの中身、再開の単位、VRAM に載せる因子は、データの流れの節で固定した。パックの前後で、量子化後の測定が親とパックを同じ入力で比べる。推論カーネルは論文の CUDA GEMV を 4060 へ移す前に、5700X の CPU で因子の行列ベクトル積を計算する。

### 分解する重み

パックに入れるテンソルは、親チェックポイントの索引で次をすべて満たすものである。

- キーが `.weight` で終わる
- 次元が 2 で、行数と列数がどちらも 32 以上
- キーが `lm_head.weight`、`model.language_model.embed_tokens.weight`、または `model.language_model.layers.N.`（N は 0 以上 44 以下）で始まる

この 3 つのキーが索引に無いときは、パックを新規作成しない。`weight_scale_inv`、1 次元の正規化とバイアス、3 次元以上の conv、層 45、`language_model` と `lm_head` の外にある画像用の塔は、分解しない。

各テンソルは、そのテンソルの重みだけから U、V、s1、s2 を作る。層をまたいで因子を共有しない。選ばれなかったエキスパートも、自分の行列として分解する。親ファイルの中で BF16 のテンソルは、その値を重みとして読む。FP8 のテンソルは、同じ接頭辞の `weight_scale_inv` を 128×128 ブロックで掛けてから分解する。BF16 の全量チェックポイント（約 642GB）は取らない。

ルーティングされるエキスパートの線形層は 42 層 × 288 体 × 3 射影で、要素数 304,405,807,104 である。ファイル全体は 328,326,771,576 バイトなので、それ以外は 23,920,964,472 バイトである。このエキスパートだけを一様な 0.55 bit で持つと 304,405,807,104 × 550 / 8000 = 20,927,899,238.4 バイトで、残りを親の dtype のまま足すと 44,848,863,710.4 バイト（約 41.8 GiB）になり、32GiB に入らない。321,323,031,390 パラメータ全体の 0.55 bit 見積もりは 22,090,958,409 バイトで、予約 4GiB を足しても 32GiB に収まる。画像用の塔と層 45 を外すと、この見積もりより小さい。索引で足す実バイトの止め方は、ゲートの節に書く。

1 行列の段は、この集合の中の 1 枚だけを測る。ゲートは行列ごとにランク、格納ビット、有限性を見る。再構成誤差の大小は合否にしない。論文の 0.55 bit の perplexity 9.82 は、前のブロックの誤差を吸収したあとの Llama-2-70B の値である。その吸収を入れない分解は、これより大きく落ちる。GLM の合格値は、この 9.82 でも、0.80 bit の 7.61 でもない。

### ビット予算

`bitsPerWeightMilli` は行列で分ける。キーに `.mlp.experts.` を含む分解する重みは 550、それ以外の分解する重みは 800 である。共有エキスパートのキーは `.mlp.shared_experts.` なので 800 である。1 行列の段の down 射影は `.mlp.experts.` に含まれるので 550 のままである。

エキスパート 304,405,807,104 要素を 800 にすると 30,440,580,711 バイトになり、32GiB から予約 4GiB を引いた 30,064,771,072 バイトを超える。550 にすると 20,927,899,239 バイトである。それ以外を最大 16,917,224,286 要素まで 800 にすると 1,691,722,429 バイトで、合計の上限は 22,619,621,668 バイトである。予約 4GiB を足しても 32GiB に収まる。画像用の塔と層 45 はこの 16,917,224,286 に含まれ、パックからは外すので、実バイトは上限より小さい。

パラメータ数でならすと、エキスパートの実効 0.52734375 bit と、それ以外の予算 0.80 bit で、平均は約 0.54 bit である。0.527 bit はエキスパート 1 枚の実効であり、モデル全体のビット数ではない。4 bit の全体は 160,661,515,695 バイトで、この RAM 常駐には入らない。使える RAM に全パラメータを置くときの平均の上限は約 0.75 bit である。

### 1 行列

測る行列は、最初の sparse 層の、ルーティングされるエキスパート 0 の down 射影である。`mlp_layer_types` の先頭 3 層は dense なので、層番号は 3（0 始まり）である。テンソル名は `model.language_model.layers.3.mlp.experts.0.down_proj.weight` と、同じ接頭辞の `weight_scale_inv` である。形は出力 4096 × 入力 2048（`hidden_size` × `moe_intermediate_size`）である。gate と up と共有エキスパートは、この 1 枚には入れない。

復元は、FP8 の値に同じ 128×128 ブロックの `weight_scale_inv` を掛けて FP32 にする。形が 4096×2048 でないとき、または復元が非有限のときは、再構成誤差を記録しない。

ランクは公開実装（SamsungLabs/NanoQuant、コミット `a9e0a430881ff80d83b622c3129e330dc33c04f5` の `calculate_ranks`）に合わせる。行数 `rows`、列数 `cols`、`bitsPerWeightMilli` に対し、

`raw = floor(rows * cols * bitsPerWeightMilli / (1000 * (rows + cols))) - 16`

とし、`raw` を 32 の倍数へ切り下げる。結果が 32 未満なら 32、`min(rows, cols)` を超えるならそこへ切る。スケールは 2 本（s1 と s2）なので、引く 16 は FP16 のスケール 1 本分である。

この行列を実効 0.55 bit（`bitsPerWeightMilli` 550）で見ると `raw` は 734、ランクは 704 である。格納ビットは `(704 + 16) * (4096 + 2048) = 4,423,680`、バイト数は 552,960 である。32 の倍数へ切ったので、この 1 枚の実効ビットは 135/256 = 0.52734375 であり、550 ミリビットの予算以下である。0.80 bit はモデル全体が予約 4GiB を足すと 32GiB に収まらないので、この 1 枚のランクには使わない。

ゲートが判定するのは、この形と 550 に対するランク 704 と、格納ビット 4,423,680 と、記録が次の形を満たすことである。親チェックポイントとパックした重みはゲートの入力にしない。再構成誤差の大小も合否にしない。記録があるとき、クラウドの親とゲートは同じ項目を読む。

ADMM の数値は同じコミットの既定に固定する。外側 400、内側 5（SVID のべき乗法）、`reg` は 0.03、ペナルティは線形でステップ `t / 400`（`t` は 0 から 399）、乱数種は 0。入力側と出力側のプレコンディショナは長さ `cols` と `rows` の 1 である。論文の Hessian 対角は校正の活性化から作る。親は約 328GB で 32GiB に載らず、1 枚の誤差を見る前に前段を走らせるとこの段の範囲を外す。校正はパックしたチェックポイントを作る段まで持たない。

ソルバ本体はこのリポジトリへコピーしない。デスクトップの測定は、固定したコミットの `factorize_admm_nanoquant` を、復元したこの 1 枚に対して呼ぶ。

再構成誤差は `‖W − Ŵ‖_F / ‖W‖_F` である。Ŵ は、均衡化のあとの因子 A（4096×704）と B（704×2048）について、符号の 0 を +1 にした U±1 と V±1、行ごとの平均絶対値 s1、列ごとの平均絶対値 s2 から `s1 ⊙ (U±1 V±1^T) ⊙ s2^T` で作る。連続因子の比は `‖W − AB‖_F / ‖W‖_F` で、同じ記録に残し、ゲートの合否には使わない。W のフロベニウスノルムが 0、または比が非有限のときは、記録を残さない。有限な比に上限は置かない。この段の誤差は、Llama-2-70B の perplexity の落ち方の代理にしない。

記録は `features/nanoquant-glm/one-matrix.json` に書き、手元の測定のあとコミットする。中身は `tensor`、`rows`、`cols`、`rank`、`bitsPerWeightMilli`、`storedBits`、`relativeError`（再構成誤差）、`continuousRelativeError`（連続因子の比）、`solverCommit`、`seed`、`device` である。ファイルが無い間は、ランクと格納ビットの契約だけをゲートが見る。ファイルがあるとき、親とゲートは次を満たすことを見る。`tensor` が層 3 エキスパート 0 の down 射影である。`rows` が 4096、`cols` が 2048、`rank` が 704、`bitsPerWeightMilli` が 550、`storedBits` が 4423680 である。`relativeError` と `continuousRelativeError` が有限である。`solverCommit` が `a9e0a430881ff80d83b622c3129e330dc33c04f5`、`seed` が 0、`device` がこの機械の GPU である。クラウドはこの JSON を再計算しない。

親チェックポイントのシャードとパックした重みは git に入れない。`.tools/` は OPA と ripgrep の取得先で、測定の置き場にはしない。

## データの流れ

親チェックポイントはディスクに置く。932GB の表記容量に対し、FP8 の約 328GB、校正で残す隠れ状態 96,636,764,160 バイト、パックの約 30GB が入る空きが要る。1 行列の段は、そのテンソルを含むシャードだけを読み、他のテンソルは展開しない。この段ではシャードを消さない。

分解する重みは、FP8 なら `weight_scale_inv` を掛け、BF16 ならその値のまま読み、連続因子とスケールを作り、±1 に量子化し、ビットパックする。順序は、親チェックポイントのベンチマーク、校正、層ごとの誤差吸収と分解、全層のあと二値を固定したスケール調整、パックのベンチマークである。親のシャードは、親のベンチマークが書けて、そのシャードに含まれるテンソルがパックされるか残す側へコピーされるまで消さない。空きが足りないとき消してよいのは、この条件を満たしたシャードだけである。

### 校正

校正はブロック分解の前に 1 回である。データは WikiText-2 raw の train、親のトークナイザ、乱数種 0 で窓を並べ、先頭から 128 本、各 2048 トークンである。論文の付録と同じ本数と長さと種である。対角は論文の式 (3) で縮め、係数 γ の初期値は 0.2 である。論文が Llama と Qwen に使った値で、GLM の値はそこには無い。

層は 1 枚ずつディスクから読む。隠れ状態は bf16 で、128×2048×4096×2 = 2,147,483,648 バイトである。入力と出力の 2 本で 4GiB。全層の入力を backward のためにディスクへ置き、45 層で 96,636,764,160 バイトである。各分解する重みの入力対角と勾配対角は fp32 で残す。校正トークンが 1 つも通らなかったエキスパートの対角は 1 にする。

1 層のルーティングされるエキスパートは FP8 で 7,247,757,312 バイトである。全部を一度に FP32 へは広げない。順伝播と逆伝播は、その層の attention と共有エキスパートを持ったまま、ルーティングされるエキスパートを 32 体ずつ読む。32 体の FP32 は 3,221,225,472 バイトである。ピークは、この組と隠れ状態 2 本と予約 4GiB である。再開の単位は層である。その層の出力隠れ状態と、その層の分解する重みすべての対角があるとき、その層はやり直さない。

### 誤差の吸収

論文の 3.2 節の順に、各ブロックで次を行う。ブロックは埋め込み、層 0 から 44 の各層、`lm_head` である。ソルバと均衡化はこのリポジトリへコピーせず、コミット `a9e0a430881ff80d83b622c3129e330dc33c04f5` を呼ぶ。

1. 誤差の吸収。現在のブロックのうち、まだ分解していない重みだけを更新し、前のブロックの量子化誤差と、同じブロックで既に分解した層の誤差を、校正で保存したそのブロックの全精度出力との差で減らす。学習率は 1e-4、バッチは 4、エポックは 8、スケジュールは cosine である。埋め込みの前にはブロックが無いので、埋め込みではこの段を飛ばす。同時に FP32 で持つルーティングされるエキスパートは 32 体までとし、組のあいだで残差を次の組のまだ分解していない重みへ渡す。attention と共有エキスパートはその層のあいだ持ち続ける。
2. 低ランクの初期化。対角があるときはそれをプレコンディショナにする。1 行列の段だけは、これまでどおり長さ `cols` と `rows` の 1 である。ADMM は外側 400、内側 5、`reg` 0.03、線形ペナルティ、乱数種 0 のままである。
3. 因子の洗練。連続因子とスケールを、そのブロックの全精度出力に合わせる。学習率は 1e-5、バッチは 1、エポックは 8、スケジュールは cosine である。

全ブロックのあと、±1 を固定したままスケールだけを調整する。学習率は 1e-6、バッチは 1、エポックは 8、スケジュールは cosine である。論文が 70B を 1 GPU に載せられたのは、この固定があるためである。

### パックの中身

出力は `features/nanoquant-glm/pack/` と `features/nanoquant-glm/calib/` に置く。どちらも git に入れない。

分解した 1 テンソルは 1 ファイルである。先頭は `rows`、`cols`、`rank`、`bitsPerWeightMilli`。続いて U の符号を行優先で 8 個ずつ 1 バイトに詰め、V も同じである。s1 と s2 は fp16 で、長さはそれぞれ `rows` と `cols` である。ファイルの長さがこの式と一致するときだけ完成とみなす。一致しないファイルは捨てる。残すテンソルは親の dtype のまま、テンソルごとに 1 ファイルでコピーする。

再開の単位は層である。層の完了印があるときはその層を飛ばす。完了印が無く、その層の完成ファイルも無いときは、誤差の吸収からやり直す。完成ファイルが一部だけあるときは、誤差の吸収を再実行せず、無いテンソルだけをキー順に分解してから完了印を書く。

### VRAM

8GiB に常時載せるのは、`.mlp.experts.` を含まない因子と、残すテンソルである。合計が 8GiB を超えるときは、`lm_head`、次に埋め込み、の順で RAM へ戻す。戻したあとも超える因子は RAM に置く。空いた VRAM には、直近のトークンが選んだエキスパートの因子を置き、空きが足りないときは最も古いものから捨てる。層 45 と画像用の塔は載せない。全エキスパートの常駐は、この機械には無い。載せる一覧とバイト数は `pack/vram.json` に書く。ゲートの合否には使わない。

出力チェックポイントの見込みは次のとおり。予約 4GiB は OS とランタイム用で、KV は別である。

| 見積もり | 重み | 32GiB RAM（予約 4GiB 後） | 8GiB VRAM |
| --- | ---: | --- | --- |
| 実効 0.55 bit | 22,090,958,409 バイト | 収まる | 収まらない |
| 論文比率を BF16 641.64 GB に適用 | 26,744,690,105 バイト | 収まる | 収まらない |
| 実効 0.80 bit | 32,132,303,139 バイト | 予約を足すと収まらない | 収まらない |

推論時はパックしたチェックポイントを RAM に置く。常時 VRAM に載せるものと、空きへ置くエキスパートは、この節の一覧のとおりである。全量を VRAM に常駐させる段は、この機械には無い。

## 量子化後の測定

親チェックポイントとパックしたチェックポイントを、同じ入力で比べる。親チェックポイントの測定は、シャードを消す前に行い、`features/nanoquant-glm/parent-benchmark.json` に書く。パックの測定は、パックができたあとに行う。Llama-2-70B の 3.32、7.61、9.82 は GLM の合格値にしない。MMLU、GSM8K、HarmBench はこの機械の測定に入れない。校正に使った train は test に混ぜない。

### 親チェックポイントの測定

データは WikiText-2 raw の test である。親チェックポイントのトークナイザで符号化し、先頭から 256 トークンを取る。最初のトークンは損失に入れない。短い生成は次の 3 つで、温度 0、新規トークン最大 32、乱数種 0、計算は CPU である。

1. `The capital of France is`
2. `日本の首都は`
3. `def add(a, b):\n    return`

順伝播は層ごとに読む。256 トークンの perplexity はチェックポイントを 1 回読む。生成は新規トークンごとに 1 回読む（最大 32 回）。常駐する重みを残し、そのトークンが選んだエキスパートだけを読むのは、層ごとの順伝播と結果が一致するときだけにする。

記録の中身は `dataset` が `wikitext-2-raw-v1`、`split` が `test`、`tokens` が 256、`parentPerplexity`、`parentPerplexityElapsedSeconds`、`prompts` がこの 3 文字列、`parentCompletions` が 3 文字列、`parentGenerationElapsedSeconds`、`seed` が 0、`device` が `cpu` である。`parentPerplexity` が有限でない、`tokens` が 256 でない、または `parentCompletions` が空でない 3 文字列でないときは、記録を残さない。手元の測定のあとコミットする。クラウドはこの JSON を再計算しない。

### perplexity

パックした重みを RAM に置き、5700X の CPU で因子の行列ベクトル積を計算する。同じ 256 トークン、同じ損失の切り方、乱数種 0 で perplexity を出す。

記録は `features/nanoquant-glm/perplexity.json` に書き、手元の測定のあとコミットする。中身は `dataset` が `wikitext-2-raw-v1`、`split` が `test`、`tokens` が 256、`parentPerplexity`（親チェックポイントの記録から写す）、`packedPerplexity`、`ratio`（`packedPerplexity / parentPerplexity`）、`packedElapsedSeconds`、`seed` が 0、`device` が `cpu` である。`packedPerplexity` または `ratio` が有限でない、または `tokens` が 256 でないときは、記録を残さない。ファイルが無い間はゲートはこの項を見ない。ファイルがあるとき、親とゲートは項目と有限性だけを見る。クラウドはこの JSON を再計算しない。256 トークンの `packedElapsedSeconds` を見るまで、test 全文は測らない。

### 短い生成

同じ 3 文を、パックした重みの CPU で、温度 0、新規トークン最大 32、乱数種 0 で生成する。`parentCompletions` は `parent-benchmark.json` から写す。

記録は `features/nanoquant-glm/generation.json` である。中身は `prompts` がこの 3 文字列、`parentCompletions` と `packedCompletions` がそれぞれ 3 文字列、`maxNewTokens` が 32、`temperature` が 0、`seed` が 0、`device` が `cpu` である。どちらかの完了文字列が空、または 3 件でないときは、記録を残さない。文面の正しさは合否にしない。ファイルが無い間はゲートはこの項を見ない。ファイルがあるとき、親とゲートは件数と空でないことだけを見る。クラウドはこの JSON を再計算しない。

### 品質

次のどれかなら、品質は悪い。`ratio` が 3 より大きい。パックの perplexity が有限でない。親チェックポイントの完了文字列が空でなく、パックの同じ文の完了文字列が空である。`ratio` が 3 以下で、パックの 3 文字列がどれも空でないときは、γ もビットも校正本数も変えない。

3 は、論文の Llama-2-70B で 9.82 / 3.32 が約 2.96 であることに合わせたやり直しの線である。GLM の合格値ではなく、ゲートの合否でもない。

悪いときは、同じ入力で測り直す。1 回のやり直しで変えるのは次のどれか 1 つである。やり直しは 3 回で止め、そのときのパックを残す。捨てた変更は回数に数えない。

1. γ を 0.2 から 0.6 にする。選べるのは現在が 0.2 のときだけである。校正の対角と、誤差の吸収と、パックをやり直す。
2. `.mlp.experts.` の `bitsPerWeightMilli` を 32 増やす。1 行列の記録は 550 とランク 704 のまま残す。増やしたあとに、分解する重みの格納バイトと残すテンソルのバイトと予約 4GiB が 32GiB を超えるときは、その変更を捨てる。超えないときは、パックの分解をやり直し、校正の対角は残す。
3. 校正の本数を 64 または 256 にする。256 のとき隠れ状態 1 本は 4,294,967,296 バイト、全層分は 193,273,528,320 バイトである。隠れ状態 2 本と、エキスパート 32 体の FP32 3,221,225,472 バイトと、予約 4GiB を足して 32GiB を超えるとき、または親チェックポイントとパックと全層の隠れ状態が表記 932GB の空きに入らないときは、256 を捨てる。捨てないときは、校正と、誤差の吸収と、パックをやり直す。

変えないものは、親チェックポイントのリポジトリ、分解する重みの範囲、ADMM の外側 400 と `reg` 0.03 と乱数種 0、ベンチマークの入力である。校正をやり直すときは、その層の出力隠れ状態と対角を消してから取り直す。パックをやり直すときは、その層の完了印と完成ファイルを消してから分解し直す。

記録は `features/nanoquant-glm/quality.json` である。中身は `changesApplied` が適用した変更の回数（0 以上 3 以下）、`attempts` が有限な `ratio` を持つ試行の配列である。各要素は `change`（`gamma-0.6`、`expert-bits-plus-32`、`calib-64`、`calib-256` のいずれか）、`parentPerplexity`、`packedPerplexity`、`ratio` である。有限でない perplexity の試行は配列に入れず、その回数は `changesApplied` に数える。ファイルが無い間はゲートはこの項を見ない。手元の測定のあとコミットする。クラウドはこの JSON を再計算しない。

## ゲート

ゲートが重みを特定するのは、学習のやり直しでも、次元ごとの損失比べでもない。親チェックポイントの索引のキーと、次元と、辺の長さだけである。校正で「どの活性化が損失に効くか」を取る手順は、ここには入らない。

索引のテンソルは次の 3 つに分かれる。

1. 分解する。キーが `.weight` で終わり、次元が 2 で両辺が 32 以上、かつ `lm_head.weight` か `model.language_model.embed_tokens.weight` か `model.language_model.layers.N.`（N は 0 以上 44 以下）である。このうちキーに `.mlp.experts.` を含むものは `bitsPerWeightMilli` 550、それ以外は 800。品質の節で `.mlp.experts.` を 32 ずつ上げたときは、その値で格納バイトを計算する。1 行列の記録は 550 のまま見る。格納バイトはランク式の `(rank + 16) * (rows + cols) / 8` である。
2. 親の dtype のままパックに残す。層 0–44 と埋め込みと `lm_head` のうち、1 に入らないもの（1 次元の正規化とバイアス、3 次元以上の conv を含む）。バイト数は索引のそのテンソルのバイト数である。
3. パックに入れない。層 45 と、`language_model` と `lm_head` の外にある画像用の塔。バイト合計にも入れない。

`lm_head.weight`、`model.language_model.embed_tokens.weight`、層 0 から 44 のいずれかのキーが索引に無いときは、パックを作らない。

止める比較は、1 の格納バイトと 2 のバイトを足し、予約 4GiB を足して 32GiB を超えるときである。超えるときはパックを作らない。形を知る前の上限は 22,619,621,668 バイト（分解する重みだけ、それ以外を最大 16,917,224,286 要素まで 800 と見た値）である。索引を走査した実バイトは、その走査の記録に残す。2 を足すとこの上限より増える。増えた合計が予約込みで 32GiB を超えるときだけ、パックを止める。

1 行列の記録があるときは、別に次を見る。テンソルが層 3 エキスパート 0 の down 射影である。`rows` が 4096、`cols` が 2048、`rank` が 704、`bitsPerWeightMilli` が 550、`storedBits` が 4423680 である。`relativeError` と `continuousRelativeError` が有限である。`solverCommit` が `a9e0a430881ff80d83b622c3129e330dc33c04f5`、`seed` が 0、`device` がこの機械の GPU である。再構成誤差の大小は合否にしない。復元が非有限、フロベニウスノルムが 0、形が 4096×2048 でないときは、記録を作らない。親のシャードとパックした重みはゲートの入力にしない。クラウドはこの JSON を再計算しない。

`parent-benchmark.json` があるときは、`tokens` が 256、`parentPerplexity` が有限、`prompts` と `parentCompletions` がそれぞれ 3 件で、完了文字列が空でないことを見る。`perplexity.json` があるときは、`packedPerplexity` と `ratio` が有限であることを見る。`generation.json` があるときは、`parentCompletions` と `packedCompletions` がそれぞれ 3 件で空でなく、`maxNewTokens` が 32、`temperature` が 0 であることを見る。`quality.json` があるときは、`changesApplied` が 3 以下で、`attempts` の各 `ratio` が有限であることを見る。比が 3 を超えることは合否にしない。ファイルが無い項は見ない。クラウドはこの JSON を再計算しない。

## 失敗時に残るもの

1. 提出前に基準を満たさないとき、状態は変わらない。親シャードが読めない、必須のキーが索引に無い、形が 4096×2048 でない、復元が非有限、1 行列の再構成誤差が有限でない、校正が 128×2048 に満たない、または分解する重みの格納バイトと残すテンソルのバイトに予約 4GiB を足して 32GiB を超えるときは、誤差の記録もパックしたチェックポイントも新規作成しない。親のベンチマークは、パックを作る前の基準である。1 行列の再構成誤差には、校正も親のベンチマークも要しない。
2. 書き戻しが失敗したとき、状態は変わらない。ADMM が非有限になった、またはパックの書き込みが途中で落ちたときは、直前の完成チェックポイントを残し、途中ファイルは捨てる。誤差の記録が途中ならそれも捨てる。
3. 状態が変わったあと、副作用だけが失敗することがある。誤差の記録が書けたあと表示が落ちても、記録は残る。チェックポイントが書けたあとパック側の perplexity または短い生成の測定が落ちても、チェックポイントは残る。`parent-benchmark.json` が無い状態を、親との比較ができたことには数えない。`perplexity.json` に `packedPerplexity` が無い状態を、パックの品質が出たことには数えない。

`node scripts/start-feature.mjs` はこのハーネス上では機能ファイルを作らない。この設計は手で置いた。プロダクト remote で `init.mjs --product` を走らせると `docs/architecture` と cycle の蓄積が消え、ハーネスのテストが赤になる。クラウドの `install` はこの初期化のあと `git checkout -- docs cycle` で戻す。コミットした cycle は `C-0001` だけである。
