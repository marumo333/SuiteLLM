# nanoquant-glm

対象は GLM-5.3-Flash（321,323,031,390 パラメータ、アクティブ 18B、45 層、ルーティングされるエキスパート 288、top-8）を、このデスクトップで推論できる格納形式にすること。手法は Samsung Research の NanoQuant（arXiv:2602.06694、2026-02）である。低ランクの二値分解で、各線形層を次の形にする。

`W ≈ s1 ⊙ (U±1 V±1^T) ⊙ s2^T`

U と V は ±1 の行列、s1 と s2 は全精度のスケールである。独立した 1bit 保存の下限（このモデルで 40,165,378,924 バイト、約 37.4 GiB）は、この分解には効かない。LittleBit（NeurIPS 2025）は同じ因子化の QAT で、公開実験は 7B〜13B 級かつ大量トークンを使う。最初の実装には入れない。

この設計が測るのは格納量だけである。GLM-5.3 に NanoQuant を当てた perplexity は、まだ無い。

## 構成

機械は AMD Ryzen 7 5700X、RAM 32GiB、NVIDIA GeForce RTX 4060 8GiB、ストレージ表記 932GB。

論文が圧縮を走らせた機械は H100 80GB が 1 枚で、対象は Llama / Qwen / Gemma の dense、最大 70B、校正は WikiText-2 の 128 サンプル（0.26M トークン）、Llama-2-70B で約 13 時間である。推論の実測は RTX 3050 8GB で、圧縮後の Llama-2-70B が最大 20.11 tok/s。本文のファイルサイズは 137.95 GB から 5.75 GB。要旨の別表記は 138.04 GB から 5.35 GB。ここでの比率は本文の 5.75 / 137.95 を使う。

WikiText-2 perplexity は Llama-2-70B の FP16 が 3.32、NanoQuant 0.80 bit が 7.61、0.55 bit が 9.82 である。GLM で同じ落ち方になるかは、このリポジトリの次の測定で決める。

親の重みは公式 FP8（約 328GB）を層ごとに読む。BF16（約 642GB）は作業用に持たない。1 つのエキスパート行列は 4060 の 8GiB に入る。モデル全体は入らない。分解は行列ごとで、結果だけをパックしてディスクへ書く。

実行の段は次の 3 つ。

1. `features/nanoquant-glm/estimate.mjs` が、ビット幅と論文の圧縮率からバイト数を出し、32GiB の RAM（予約 4GiB）と 8GiB の VRAM に収まるかを返す。この段は実装済み。
2. FP8 から 1 層を読み、1 つのエキスパート行列を ADMM で初期化し、再構成誤差を記録する。誤差を見る前に全層は走らせない。
3. 全層を同じ手順で流し、パックしたチェックポイントを書く。推論カーネルは論文の CUDA GEMV を 4060 へ移す前に、5700X の CPU で因子の行列ベクトル積を計算して perplexity を取る。

## データの流れ

親チェックポイントはディスクに置く。932GB の表記容量に対し、FP8 の約 328GB と出力の約 30GB が入る空きが要る。空きが足りないときは、読んだシャードを分解のあと消す。

各行列は FP8 から復元し、連続因子とスケールを作り、±1 に量子化し、ビットパックする。校正活性化は 128 サンプル分だけを保持する。グローバルなスケール調整は、パック済みの二値を固定したまま行う。論文が 70B を 1 GPU に載せられたのは、この固定があるためである。

出力チェックポイントの見込みは次のとおり。予約 4GiB は OS とランタイム用で、KV は別である。

| 見積もり | 重み | 32GiB RAM（予約 4GiB 後） | 8GiB VRAM |
| --- | ---: | --- | --- |
| 実効 0.55 bit | 22,090,958,409 バイト | 収まる | 収まらない |
| 論文比率を BF16 641.64 GB に適用 | 26,744,690,105 バイト | 収まる | 収まらない |
| 実効 0.80 bit | 32,132,303,139 バイト | 予約を足すと収まらない | 収まらない |

推論時はパックしたチェックポイントを RAM に置き、よく使う因子だけを 8GiB の VRAM に載せる。全量を VRAM に常駐させる段は、この機械には無い。

## 失敗時に残るもの

1. 提出前に基準を満たさないとき、状態は変わらない。親シャードが読めない、校正サンプルが 128 に満たない、または 1 行列の再構成誤差が記録されていないときは、チェックポイントを新規作成しない。
2. 書き戻しが失敗したとき、状態は変わらない。ADMM が発散した、またはパックの書き込みが途中で落ちたときは、直前の完成チェックポイントを残し、途中ファイルは捨てる。
3. 状態が変わったあと、副作用だけが失敗することがある。チェックポイントが書けたあと perplexity の測定が落ちても、チェックポイントは残る。測定ファイルが無い状態を、品質が出たことには数えない。

`node scripts/start-feature.mjs` はこのハーネス上では機能ファイルを作らない。この設計は手で置いた。プロダクト remote で `init.mjs --product` を走らせると `docs/architecture` と cycle の蓄積が消え、ハーネスのテストが赤になる。クラウドの `install` はこの初期化のあと `git checkout -- docs cycle` で戻す。コミットした cycle は `C-0001` だけである。
